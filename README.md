# Plan-and-Execute DevOps-агент з persistence, agentic RAG та HITL

## 1. Опис проєкту

Продовження [ДЗ №1](../hw2) (ReAct DevOps-асистент): той самий домен, але
архітектура Plan-and-Execute замість ReAct. Агент СПОЧАТКУ складає повний
план виконання задачі, а ПОТІМ виконує його крок за кроком, адаптуючи план
на основі проміжних результатів (replanning). Побудований на OpenAI GPT-4.1.

Додано три production-критичні можливості:
- **Persistence** — стан агента зберігається у SQLite (`SqliteSaver`) і
  переживає "перезапуск" процесу.
- **Agentic RAG** — агент самостійно вирішує, коли звертатися до бази
  знань (ChromaDB) замість "живих" tools.
- **Human-in-the-Loop** — ризикова дія (`deploy_service`) зупиняє граф і
  чекає підтвердження людини перед виконанням.

## 2. Архітектура (planner / executor / replanner)

Граф: `START → planner → executor → replanner → (executor | END)`

- **`planner`** (`plan_execute.py`) — приймає запит користувача, викликає
  LLM з `with_structured_output(Plan)` і генерує `Plan(goal, steps)`:
  ціль та список 2-5 конкретних, виконуваних кроків.
- **`executor`** — бере крок `plan[current_step]`, викликає LLM з
  `bind_tools(...)` і виконує обраний(і) tool(и); результат додається до
  `results`, `current_step` збільшується на 1.
- **`replanner`** — викликає LLM з `with_structured_output(ReplanDecision)`,
  аналізує прогрес (`plan`, `results`, скільки кроків залишилось) і
  повертає `action`: `continue` (виконати наступний крок як є), `replan`
  (замінити залишкові кроки на `updated_steps`) або `finish` (ціль вже
  досягнута, завершити достроково).
- Router `should_end` веде назад на `executor`, поки `completed=False`.

Ключова відмінність від ReAct (ДЗ №1): у ReAct LLM вирішує наступну дію
"на льоту", бачачи лише останній результат. Тут план складається одразу
цілком, і replanner explicit оцінює прогрес відносно ВСЬОГО плану — це
дає передбачуваність (видно весь план заздалегідь) ціною гнучкості
(перший крок не бачить результатів майбутніх кроків).

`hitl.py` перевикористовує `planner_node`/`replanner_node` з
`plan_execute.py` і підміняє тільки `executor` на `executor_with_hitl`,
яка додатково перевіряє, чи виклик tool ризиковий.

## 3. Домен та інструменти

Той самий DevOps-домен, що й у ДЗ №1:
- `check_service_status`, `get_deployment_info`, `analyze_logs`,
  `calculate_uptime` — "живі" дані (мок-реєстр, `tools.py`)
- `search_knowledge` — RAG-tool до бази знань (`knowledge.py`)
- `deploy_service` — **РИЗИКОВИЙ** tool, потребує підтвердження людини

### База знань (ChromaDB)

10 документів (`knowledge.py`, colecction `devops_knowledge`,
`chromadb.PersistentClient` для кешу embeddings між запусками) —
DevOps-політики та процедури, які НЕ змінюються в реальному часі (на
відміну від tools.py): вікна деплою, рівні серйозності інцидентів,
процедура ескалації, SLA, rollback-процедура, post-mortem процес,
права доступу на деплой, backup-політика, конвенції іменування,
політика алертів.

### Ризиковий tool: `deploy_service`

Деплой нової версії сервісу в будь-якому середовищі — незворотна дія
(перезаписує "поточну версію" у мок-реєстрі), яка в реальному DevOps
може спричинити downtime чи регресію. Тому будь-який виклик
`deploy_service` перехоплюється `executor_with_hitl` через `interrupt()`
ДО фактичного виконання.

## 4. Персистентність (SqliteSaver)

`plan_execute.py` та `hitl.py` компілюють граф з
`checkpointer=SqliteSaver(sqlite3.connect("agent_state.db"))` (файл, а
не `:memory:` — інакше стан втрачається при завершенні процесу).
`thread_id` у `config={"configurable": {"thread_id": ...}}` ідентифікує
незалежну сесію — різні `thread_id` мають повністю ізольований стан
(перевірено: `session-002` до першого запуску повертає порожній
`state.values`, незважаючи на те, що `session-001` вже виконав 4 кроки).

Обов'язкова для HITL: `interrupt()` зупиняє виконання графа, і без
checkpointer стан між `interrupt()` та `Command(resume=...)` не
зберігається взагалі.

## 5. Human-in-the-Loop: flow

1. `executor_with_hitl` викликає LLM з tools (включно з `deploy_service`).
2. Якщо LLM повертає `tool_call` для tool із `RISKY_TOOLS`, виконання
   зупиняється через `interrupt({"action", "args", "message"})` —
   граф зберігає стан і повертає керування з `result["__interrupt__"]`.
3. Людина отримує деталі дії (`interrupt_data["message"]`) і приймає
   рішення:
   - **approve** — `Command(resume={"approved": True})` → tool
     виконується як задумано.
   - **reject** — `Command(resume={"approved": False, "reason": "..."})`
     → tool НЕ виконується, у `results` записується явна відмова з
     причиною, і replanner/executor адаптують подальші кроки.
   - **edit** — `Command(resume={"approved": True, "edited_args": {...}})`
     → tool виконується, але з параметрами, зміненими людиною (у наших
     тестах: людина виправила версію `v1.0.0` → `v1.0.1` перед деплоєм).
4. Executor node виконується ПОВТОРНО з початку при resume (так працює
   `interrupt()` у LangGraph — весь виклик вузла відтворюється заново,
   але сам виклик `interrupt()` повертає кешоване значення замість
   повторної зупинки).

## 6. Інструкція запуску

```bash
cd hw4
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

Додати ключ у `.env`: `OPENAI_API_KEY=sk-...`

```bash
python3 tools.py        # unit-тести/демо tools (без API-ключа)
python3 knowledge.py    # ChromaDB: завантаження бази знань + тест RAG-пошуку
python3 plan_execute.py # Завдання 1 (planner-executor-replanner) + Завдання 2 (persistence)
python3 hitl.py         # Завдання 4: HITL approve / reject / edit сценарії
```

Кожен запуск `plan_execute.py`/`hitl.py` дописує стан у `agent_state.db`
(persistence across runs — саме тому файл, а не `:memory:`).

## 7. Аналіз результатів

**Чи генерує planner адекватний план?**
Так. Наприклад, для "Задеплой нову версію v2.15.0 сервісу api-gateway в
продакшн" planner склав план з 4 кроків: перевірити поточний статус →
перевірити наявність артефакту в реєстрі → виконати деплой → перевірити
стан після деплою. Це відповідає реальній DevOps-практиці (health-check
перед деплоєм, деплой, health-check після).

**Чи адаптує replanner план на основі результатів?**
Так, спостережено реальний `replan` (не лише `continue`/`finish`): у
сценарії EDIT, коли людина підтвердила деплой з версією `v1.0.1` замість
запитаної `v1.0.0`, replanner помітив розбіжність між планом (ціль —
задеплоїти v1.0.0) і фактичним результатом (задеплоєно v1.0.1) і
самостійно ДОДАВ нові кроки: "Оцінити, чому задеплоєно версію v1.0.1
замість цільової v1.0.0" та "З'ясувати, чи можливо задеплоїти саме
v1.0.0". План зріс з 5 запланованих кроків до 10 виконаних — явна
демонстрація адаптивного replanning, а не сліпого виконання
початкового плану.

**Persistence: чи справді відновлюється стан?**
Так. Перший запуск (`session-001`) виконав повний план (4/4 кроки) і
завершився. Друге, окреме з'єднання (`sqlite3.connect` наново до того ж
`agent_state.db`) успішно прочитало через `get_state()` повний
збережений `plan`, `current_step=4` та всі `results` — симуляція
"перезапуску процесу" підтверджує, що стан дійсно на диску, а не тільки
в пам'яті. Незалежний `thread_id` (`session-002`) до першого запуску
повернув порожній стан, підтверджуючи ізоляцію сесій.

**Чи агент САМОСТІЙНО вирішує RAG vs tool?**
Так — жодного явного інструктажу "використай RAG" не було. У тесті з
запитом про причину недоступності auth-service агент викликав
`analyze_logs`/`check_service_status` для "живих" даних, а окремо для
запитів про політики (вікно деплою, права доступу, SLA) — самостійно
викликав `search_knowledge`. Жодного разу агент не намагався
"вигадати" відповідь на політичне питання без звернення до бази знань.

**HITL: чи всі три сценарії відпрацювали коректно?**
- **Approve** — `deploy_service` виконано з оригінальними параметрами
  одразу після підтвердження.
- **Reject** — `deploy_service` НЕ виконано, у результатах записано
  `"ВІДХИЛЕНО оператором (причина: Поза вікном деплою)"`, і подальші
  кроки плану коректно відреагували (агент шукав інформацію про
  політику вікон деплою через `search_knowledge` і чекав на нове
  підтвердження, а не проігнорував відмову).
- **Edit** — `deploy_service` виконано зі ЗМІНЕНОЮ людиною версією
  (`v1.0.1` замість запитаної `v1.0.0`), що підтверджено у
  `get_deployment_info` після деплою.

## 8. Висновки та обмеження

- **Що працює добре:** структуровані outputs (`Plan`, `ReplanDecision`)
  надійно повертають валідні Pydantic-об'єкти; persistence і
  незалежність `thread_id` підтверджені прямим тестом; HITL
  interrupt/resume коректно призупиняє й відновлює виконання з диска;
  replanner здатний реагувати на розбіжність між планом і фактичним
  результатом (а не сліпо йти за початковим планом).
- **Обмеження №1 (планування):** planner іноді включає в план крок,
  для якого немає відповідного tool (наприклад, "перевірити наявність
  docker-образу в реєстрі" — такого tool не існує). У цьому випадку
  executor LLM просто відповідає текстом-уточненням замість виклику
  tool. Це не ламає граф, але робить окремі кроки "марними". Можливе
  покращення: явно передавати planner-у список доступних tools у
  промпті, щоб він планував тільки виконувані кроки.
- **Обмеження №2 (надійність HITL-тригера):** захист `interrupt()`
  спрацьовує лише тоді, коли LLM РЕАЛЬНО повертає `tool_call` для
  ризикового tool. В одному з тестових прогонів LLM замість виклику
  `deploy_service` для сервісу, який мав статус "down", написав текст
  "чи можна продовжувати з деплоєм?" замість виклику tool — інтерпрет
  просто не спрацював, і жодна дія (ні дозволена, ні відхилена) не
  відбулася. Це safe-за-замовчуванням (нічого ризикованого не
  сталося), але означає, що демонстрація HITL найнадійніша на чітких,
  однозначних формулюваннях кроку; для production варто розглянути
  `tool_choice="required"` на кроках, явно позначених як ризикові в
  плані.
- **Обмеження №3 (якість embeddings):** ChromaDB за замовчуванням
  використовує `all-MiniLM-L6-v2` — модель, оптимізовану переважно під
  англійську мову. На українських запитах семантичний пошук іноді
  повертає релевантний документ не на першому місці (спостережено для
  запиту про rollback-процедуру). Для production варто розглянути
  мультимовну embedding-модель.
- **Відоме обмеження interrupt():** LangGraph повторно виконує ВЕСЬ
  вузол `executor` з початку при resume (включно з LLM-викликом ДО
  `interrupt()`). У наших тестах повторний LLM-виклик щоразу повертав
  той самий tool_call (детерміновано при `temperature=0.1`), але
  теоретично він може відрізнятися — це задокументована особливість
  LangGraph, а не помилка нашої реалізації.

## 9. Структура файлів

- `tools.py` — Tools з Pydantic-схемами (включно з ризиковим `deploy_service`)
- `knowledge.py` — ChromaDB + `search_knowledge` tool (Завдання 3)
- `plan_execute.py` — LangGraph: planner + executor + replanner, persistence (Завдання 1, 2)
- `hitl.py` — Human-in-the-Loop з `interrupt()`/`Command` (Завдання 4)
- `agent_state.db` — SQLite з збереженим станом (генерується)
- `chroma_db/` — кеш embeddings ChromaDB (генерується, не є частиною здачі)
